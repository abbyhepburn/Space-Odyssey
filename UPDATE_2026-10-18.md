# Space Odyssey fixes — October 18, 2026

This source combines `main` (`b0dda72`) with the complete
`feature/opencv-implementation` branch (`8c0ba1b`) and the additional fixes below.
It has not been pushed, merged on GitHub, or deployed. The connected GitHub
installation reported read-only repository access.

## Changes

- The launch shows a rocket ascending from Earth's limb into space, driven by
  the server launch clock. The astronaut-hand intro is gone. The 3D cockpit
  departure follows before free flight.
- A dedicated “Gemini is getting your game ready” popup appears from planet
  selection through preparation, then the tutorial opens. Local fallback games
  still work without an API key.
- Both controllers can click on-screen buttons and links using the full-screen
  raw joystick cursor. The next joystick press dismisses an open
  information/manual/log panel; otherwise it starts a tutorial or leaves results.
  Simultaneous presses cannot click through two panels. Opening a local panel
  prevents its joystick movements from piloting the ship underneath it.
- Discrete button clicks are routed to the frontend in **every phase**, including
  a running mission, while it is connected and renewing its UI context. The
  cursor can activate buttons, links, tab controls and expandable setup/MPU
  summaries. The topmost control highlights as you aim; panels block clicks to
  controls underneath them. Click position is captured at button-down, so later
  joystick movement cannot shift the target. A disabled control does nothing.
  During a mission, a click away from UI forwards exactly one gameplay PRESS for
  that same player. Both players' simultaneous gameplay presses are retained.
  With an information panel open, the next joystick press closes it. Menu click
  counters are session-scoped; old clicks are ignored on reconnection.
- The bottom camera tab is removed. Optional camera setup is inside **Controller
  setup**. OpenCV runs in its own laptop window. The browser camera popup button
  has been removed from the game. `?camera=1` now actually opens the browser
  camera page. Camera lifetime survives launch/menu transitions.
- The worker and standalone OpenCV paths use the shared shoulder detector and
  two-player assignment; jump/duck events reach the same game authority. The
  worker preserves actionable error messages and refreshes held duck states.
- MPU health/acceleration/gyro telemetry is carried through the extended BLE
  packet and USB parser and displayed with its own freshness timer. Missing
  telemetry, stale data and failed reads are visibly distinct.
- Both remote sketches lower flick activation from **5.0 to 2.5 m/s²** relative
  to calibrated rest, release from **1.8 to 0.8**, and left/right tilt activation
  from **18° to 12°**, release from **11° to 7°**. Shake retains its two-peak
  hysteresis/cooldown. Failed IMU reads neutralize tilt and reset its latch;
  startup failures retry the sensor every five seconds.
  Recovery calibration samples run across loop iterations so joystick/button
  sampling and BLE advertising keep running while the controller settles.
- Leaving a planet cancels pending generation, clears held poses, returns to
  space 65 units outside that planet and faces the ship away from it. Either
  player's button can leave the winner panel.
- Planet Log lists the eight planets, visits and the two scores/winner from
  each planet's **first completed round**. Replays never replace that result.
  An abandoned round does not assign a win. Records last for the expedition;
  explicit Restart Expedition/server restart starts a new record. There is no
  cross-device account/database persistence.

## Install this update

Use the whole updated project, including `shared/`, frontend, backend and
hardware. Preserve your existing `backend/.env`; none is supplied in this ZIP.
Do not combine the newer firmware with the older default-branch game code.

1. Install backend dependencies: `python -m pip install -r backend/requirements.txt`.
2. Install/build the frontend: `cd frontend`, `npm ci`, `npm run build`.
3. For OpenCV, install `backend/requirements-vision.txt` in that **same Python
   environment**, then run `python backend/download_pose_model.py` once.
4. Reflash **both ESP32 remotes and Pico 2 W** from `hardware/` in this update.
   Keep each sketch folder intact. P1 uses MPU6050 and P2 MPU9250 in these
   repository sketches; check your actual sensor and pin definitions before
   uploading. Keep remotes still and sticks centered during startup/recovery.
5. Start the local game with `python start_game.py --serial COM3 --camera`
   (replace COM3 with your Pico's actual port; on Mac use `/dev/cu.usbmodem…`).
   Omit `--camera` for remote-only mode. Close Arduino Serial Monitor first.
6. For hosted mode, rebuild/redeploy this same source before pairing the laptop.
   Use `--cloud https://spaceodyssey.work` and the website's current pairing code.
   Open the camera through the launcher or Controller setup, rather than a
   bottom tab. The supplied ZIP does not change the currently deployed website.

## Board bench check

First check the Pico Serial Monitor for `REMOTE,Pn,STATE,…` and
`REMOTE,Pn,MPU,1,…`. A 0 health flag means an I2C read failed; no MPU lines means
an older firmware packet is being received. Confirm that both ESPs **and** the
Pico have this version before troubleshooting the website. Check P1/P2 identity,
SDA/SCL, common ground, module voltage and address 0x68/0x69.

Then test tilt, shake and flick while watching each remote's own Serial Monitor
for event logs. `FLICK_AXIS` and `FLICK_SIGN` in each sketch describe mounting
orientation and may need adjustment for your grip. Lower sensitivity alone
cannot fix wrong wiring or axis orientation. After closing Serial Monitor,
pair USB, check MPU data and test each gesture in a matching planet challenge.
These are BLE broadcasts with sequence deduplication, not reliable connected
delivery; measure missed events with the actual two-controller setup.

For a direct USB movement check (with the game bridge and Serial Monitor closed),
run `python backend/controller_check.py COM3 --seconds 30`. Move both sticks,
tilt both remotes, shake them and press their buttons. It reports what arrived
on the actual Pico USB stream, and exits unsuccessfully unless it saw state,
tilt, shake and a button from **both** players. This script does not flash boards.
Your Pico port is **`/dev/cu.usbmodem101` on the Mac**. This development session
is Windows, so it cannot access that macOS device directly. On the Mac, close
the game bridge and Serial Monitor, then use the same Python environment as
the backend to run:

```sh
backend/.venv/bin/python backend/controller_check.py /dev/cu.usbmodem101 --seconds 30
```

After the check releases the port, start the game/bridge using:

```sh
backend/.venv/bin/python start_game.py --serial /dev/cu.usbmodem101 --camera
```

Use `python3` in place of `backend/.venv/bin/python` if your installed backend
environment is already active. A successful simulated test does not mean these
physical-controller checks have been performed.

Browser-native fullscreen and camera permission prompts still require browser
approval/user interaction. Joystick clicks invoke the corresponding app button,
but cannot bypass those browser restrictions.
